STAMP — Fundamentos → finalidade / FTA vs STPA
Acidentes NÃO são apenas cadeias de falhas — surgem de interações inseguras entre componentes que funcionam corretamente.
Segurança = problema de controle dinâmico hierárquico, não prevenção de falhas isoladas.
STPA (proativo, antes do acidente) · CAST (retroativo, pós-acidente)
FTA/FMEA
Bottom-up · causa=falha · usa probabilidade · humano=falha · pós-design
STPA
Top-down · causa=controle inadequado · sem prob. · humano=controlador · desde conceito
STPA encontra tudo que FTA/FMEA encontra + cenários sem falha de componente.
STPA — 4 Passos (sempre sequenciais) → passos / ordem
1
Propósito: Perdas → Hazards → Restrições
2
Estrutura de controle: hierarquia + feedback
3
UCAs: ações de controle inseguras (4 tipos) — O QUÊ
4
Cenários: causas das UCAs — POR QUÊ
Rastreabilidade: Cenário → UCA → Hazard → Perda → Requisito
Passo 1a — Perdas (Losses) → perda / loss
Resultado inaceitável para qualquer stakeholder. Ex: L-1 morte, L-2 dano ao veículo, L-3 dano ambiental.
Perda = resultado final indesejado (NÃO é causa, NÃO cita componente)
"Falha de freio" ≠ perda. Perda seria: "morte do passageiro".
Passo 1b — Hazards (Perigos) → hazard / perigo
Hazard = <Sistema> + <Condição insegura> + [→ Perdas]
Estado/condição do SISTEMA que, no pior caso ambiental, leva a uma perda.
NÃO é causa, NÃO é evento externo, NÃO é componente.
Erros: usar "inseguro" na definição · mais de 10 hazards · citar componente específico
Ex correto: "Veículo próximo a pedestre em velocidade excessiva → L-1, L-2"
Passo 1c — Restrições de Segurança → restrição / constraint
Safety Constraint = inversão do Hazard: o que o sistema DEVE garantir
H-1 → SC-1: inverte a condição. Não especifica solução, apenas restrição.
H-1 "veículo rápido perto de pedestre" → SC-1 "manter velocidade segura próximo a pedestres"
Passo 2 — Estrutura de Controle → estrutura / controlador
Modelo funcional (NÃO físico) do sistema como laços de feedback hierárquicos.
Setas ↓ = ações de controle · Setas ↑ = feedback
Controlador
Toma decisões; tem modelo de processo interno (crença — pode estar ERRADO)
Algoritmo
Lógica de decisão (código, regras, procedimentos)
Atuador
Executa a ação no processo físico
Sensor
Captura estado → envia feedback ao controlador
Sociotécnico
Reguladores → Empresa → Gestão → Operações → Sistema físico
Operacional
Foco nos componentes de controle em tempo real
Problemas: controlador sem feedback · controladores com comandos conflitantes · modelo de processo desatualizado
Passo 3 — UCAs → UCA / ação insegura
UCA = <Controlador> + <Ação> + <Contexto> + [→ Hazard]
TipoDefiniçãoExemplo
T1Não fornecida quando deveriaFreio não acionado com obstáculo
T2Fornecida quando não deveriaFreio acionado sem obstáculo
T3Cedo / tarde / ordem erradaFreio tarde demais para parar
T4Duração incorretaFreio liberado antes de parar
Contexto é essencial: mesma ação pode ser segura ou insegura conforme estado do sistema.
UCAs = O QUÊ é inseguro. Passo 4 = POR QUÊ. UCAs geram Restrições de Controle.
Passo 4 — Cenários de Perda → cenário / causa / execução
Tipo 1
Por que o controlador emitiu a UCA (falha no caminho de controle)
Tipo 2
Ação correta, mas não executada adequadamente (falha no atuador/canal)
Fontes Tipo 1 (controlador errou):
Modelo de processo errado (crença ≠ realidade)
Feedback incorreto/atrasado/ausente
Lógica incorreta no algoritmo
Conflito entre controladores simultâneos
Fontes Tipo 2 (execução falhou):
Falha mecânica/elétrica do atuador
Perturbação externa impede execução
Atraso no canal controlador→atuador
Definições — consulta rápida → definição / conceito
Perda
Resultado inaceitável para stakeholder. O QUE se quer evitar.
Hazard
Estado/condição do SISTEMA que, no pior caso, leva à perda. Não é causa.
S. Constraint
Inversão do hazard: o que o sistema DEVE satisfazer.
UCA
Ação de controle que, em dado contexto, contribui para hazard. 4 tipos.
Mod. processo
CRENÇA do controlador sobre estado do sistema. Pode estar ERRADO.
Mod. mental
Crença específica do controlador humano. Influencia percepção e decisão.
Prop. emergente
Surge somente das interações — não existe em componente isolado.
Safety
Perdas físicas/operacionais NÃO intencionais.
Security
Proteção contra ameaças INTENCIONAIS. Tríade CIA: Confidencialidade, Integridade, Disponibilidade.
Stakeholder
Qualquer indivíduo/grupo/org. com interesse legítimo no sistema (direto ou indireto).
Cenário perda
Explicação causal de por que UCA ocorre (T1) ou por que ação correta falha (T2).
Engenharia de Requisitos → requisito / especificação
Elicitação
Descoberta com stakeholders (entrevistas, prototipagem, workshops)
Especificação
Documentação clara e rastreável — NÃO substitui elicitação
Validação
Verificação de que req. refletem necessidades reais
Scrubbing
Seleção e refinamento dos requisitos mais consistentes e viáveis
Funcionais
O QUÊ o sistema faz: funcionalidades e comportamentos
Não-funcionais
COMO opera: desempenho, segurança, usabilidade
Ambíguos
RISCO: múltiplas interpretações → sistema pode não atender necessidades reais
Capability Gap
Diferença entre capacidade ATUAL e capacidade NECESSÁRIA. Base para priorização.
Prototipagem
Apoio VISUAL à elicitação. NÃO substitui documentação. NÃO elimina validação.
Ferramentas
Organização, rastreamento e controle de alterações ao longo do ciclo de vida.
⚠ Pegadinhas — erro × correto ✓ → alternativas erradas
× "Falha de freio" é hazard → ✓ Hazard é ESTADO: "veículo não desacelera suficientemente"
× Perda = Hazard → ✓ Hazard LEVA À perda (causal, não sinônimos)
× UCA sem contexto → ✓ UCA: controlador + ação + contexto + hazard
× Estrutura = diagrama físico → ✓ É modelo FUNCIONAL hierárquico
× Modelo de processo é confiável → ✓ É CRENÇA — pode divergir da realidade
× STPA só detecta falhas de componentes → ✓ Detecta interações inseguras SEM falhas
× Safety = Security → ✓ Safety=não-intencional · Security=intencional (CIA)
× Passo 3 = POR QUÊ UCA ocorre → ✓ P3=O QUÊ · P4=POR QUÊ
× Prototipagem substitui documentação → ✓ Apoio à elicitação
× Req. ambíguo é útil → ✓ Aumenta risco de produto errado
× Stakeholders = só usuários finais → ✓ Qualquer parte com interesse legítimo
Controladores humanos na STPA → humano / controlador
Tratados como controladores ativos — têm responsabilidades, modelo mental e interações que influenciam o sistema.
NÃO são ignorados por dificultar modelagem.
NÃO são apenas fontes de erro como em FTA/FMEA.
Cenários com adversários → adversário / security / spoofing
Extensão do STPA para ameaças intencionais. Mesmos 4 passos.
Spoofing: falsificação de sinal de sensor → enganar modelo de processo.
Injeção de comando: adversário insere ação de controle falsa.
Adversarial ≠ acidental. Ambos geram UCAs.
Resultados da STPA → resultado / uso / saída
Requisitos de segurança derivados das restrições de controle
Orientações de arquitetura: onde colocar redundância/monitores
Casos de teste: cada cenário gera um caso de teste
Rastreabilidade total: requisito → hazard → perda
MicroSTAMP: ferramenta MIT. Modela estrutura graficamente + organiza tabelas rastreáveis.
